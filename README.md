# 4d-plugin-stomp

A reusable reference for reviewing a compiled 4D plugin's C/C++ source for memory leaks, crashes/freezes, and API-misuse; triaging a failed CI build's log output back to a root cause and fix; and (optionally) producing 4D-facing command documentation. Organized as recognizable error signatures and generalizable rules, each with the minimum concrete detail needed to apply it — written for whoever (human or Claude) repeats this process on a different 4D plugin.

Companion document: `4d-plugin-doc-style-guide.md` governs the *documentation* half of this workflow (§8 below) — this file governs the *code review* half and how the two connect.

---

## 1. Scope of the review

When a user hands over 4D plugin source (typically a `.cpp`/`.h` pair generated by 4D's Plugin Wizard, plus a `manifest.json`) and asks for a review, the default framing is:

- Memory leaks
- Vulnerabilities/slowness/freeze/crash risk
- API usage correctness — specifically **system or 3rd-party API calls** and **C/C++ conventions**
- Assume the plugin SDK itself (`4DPluginAPI.h/.c`) is trustworthy *unless the user later supplies it* — then verify claims about it instead of assuming.
- **4D itself has no Linux runtime.** Source gated on `VERSIONMAC`/`VERSIONWIN` with no `#else`/Linux branch is complete, not a gap — don't flag "missing Linux support" as a finding. If a project's target platforms are ever ambiguous, ask rather than assume, but the default for 4D plugins specifically is Mac + Windows only.

Do not expand scope to a full architectural critique or style opinions unless asked. Stay concrete and cite line-level evidence for every claim.

## 2. Research before writing a single finding

The plugin's actual C++ file is generated by 4D's Plugin Wizard and dispatches on a `selector` inside `PluginMain`. Before evaluating anything:

1. **Read the full dispatch table** in `PluginMain`'s `switch(selector)` to know the complete, authoritative command surface — don't infer it from the header comment block or the manifest alone.
2. **Read every function the dispatch calls, end to end**, not just its signature — parameter extraction, control flow, all platform branches (`#if VERSIONMAC` / `#if VERSIONWIN`), and the return path.
3. **Trace ownership and lifetime of every SDK-provided handle** (`PA_Picture`, `PA_ObjectRef`, `PA_CollectionRef`, native platform image types like `CGImageRef`/`Gdiplus::Bitmap*`) from creation to disposal. A leak claim requires seeing the full lifetime, not just "no dispose call nearby."
4. **Do not assume the SDK's API semantics from the function name alone.** A function like `PA_DuplicatePicture` sounds like "always allocates a new object," but its actual header comment and implementation can show it means "retain the same object" depending on an argument (e.g. a `retainOnly` flag). If the SDK header/implementation is available, read it before asserting a leak; if it isn't, say the claim is provisional and ask for it rather than stating it as fact.
5. **Check for exception-safety across the plugin/host boundary.** 4D plugins are typically called from a top-level `try { switch(selector) ... } catch(...) {}` in `PluginMain`. If the callee can throw, and the catch-all swallows it *without having already called the SDK's "return value" function* (`PA_Return*`), the host application will hang/freeze waiting for a return that never comes — a materially different (and often more severe) failure mode than a crash, worth calling out as such rather than lumping it in with generic "add error handling" advice.
6. **Check platform-specific data-format handling for correctness, not just presence of a code path.** E.g. a Windows GDI+ branch that special-cases `PixelFormat8bppIndexed` needs to actually resolve palette indices through the real palette (`Bitmap::GetPalette`) — copying raw index bytes as if they were already grayscale intensities compiles fine and looks reasonable but is silently wrong for any non-identity palette.
7. **Check for uninitialized variables that are currently "safe" only by accident of the call sites in scope** (e.g. a `bool success;` only ever reached via two `if/else` branches that both assign it) — flag these as latent bugs even when not currently reachable as uninitialized-read paths, since refactors are exactly what turns a latent bug live.
8. **Check narrow/wide string conversions built by hand** (e.g. a UTF-16 literal constructed as an interleaved-null narrow-string literal like `".\0b\0m\0p\0\0\0"`) — these compile silently wrong if a null byte is mis-counted, with zero compiler diagnostic. Flag them even though they "currently work," because they're a maintenance trap, and prefer a compiler-verified alternative (`u"..."` literal) if fixing.
9. **Do not flag theoretical-only issues as if they were live risks.** E.g. a `(PA_long32)size_t` truncation is only relevant past a multi-gigabyte buffer — note it exists, but don't rank it alongside a freeze-causing exception-swallow.
10. **When verifying a third-party API claim (leak ownership, function existence, parameter type), check the project's own vendored copy at the exact tag/commit being built — not just the upstream library's current master branch.** These can diverge silently — a header fix correctly derived from a library's upstream `master` can still fail CI because the project's actual checked-out tag vendors an older release whose header predates the API being relied on. **Whenever a CI log or checkout step reveals a specific tag/commit/ref, fetch dependency headers at that exact ref, not `HEAD`/`master`, if the finding depends on their contents.**
11. **Any numeric value taken from a 4D-supplied parameter (an object field via `ob_get_n`, a direct scalar parameter, etc.) and used to size an allocation or buffer must be validated *before* it's cast to an unsigned/size type.** `ob_get_n` and friends return a `double` straight from caller-controlled input — casting a negative, NaN, or `Inf` `double` to `size_t` is undefined behavior (not a guaranteed wraparound), and an unvalidated huge value flowing into `buf.resize(size)` is a real DoS/freeze vector (`std::bad_alloc`/`std::length_error`), reachable from an ordinary 4D method call with no special privilege. Validate with `std::isfinite`, `>= 0`, and an explicit upper bound *before* the cast, and reject/clamp rather than proceeding. This is a higher-priority class of finding than the general "exception-safety" point (§2.5) because it's the thing most likely to actually trigger that exception in practice.
12. **Check whether a value validated against one bound is later handed to a *different* system API with a narrower native parameter type.** E.g. a `size` capped well below `SIZE_MAX` may still need checking against `ULONG_MAX` before being passed as a Windows API's 32-bit `ULONG` parameter — a `size_t`-to-`ULONG` narrowing that would otherwise silently truncate the count. One validation pass doesn't automatically clear every downstream consumer of the same value if their native parameter widths differ.
13. **Recognize per-call open/close of an OS-level handle or provider as a performance finding, not just a style nit, and check whether the platform API offers a stateless/handle-free alternative before recommending a persistent-handle redesign.** E.g. `BCryptOpenAlgorithmProvider`/`BCryptCloseAlgorithmProvider` on every invocation of a "generate random" command is a real syscall-level cost paid per call, worth flagging if the command could plausibly be called in a loop — but check first whether the platform vendor documents a stateless call that avoids the handle entirely (`BCryptGenRandom(NULL, ...)` is Microsoft's own documented recommended usage for exactly this case); the simpler fix should win when it exists and covers the same need.
14. **A "no dispose needed" comment left by the original author is not itself evidence — the SDK's own constructor implementation can settle it.** A variable-kind-dependent SDK factory function (e.g. `PA_CreateVariable`, dispatching on `PA_VariableKind`) must be checked per the specific kind constant actually used at the call site, not treated as leak/no-leak uniformly across every kind it can construct — some kinds only assign into a union (no heap resource), others allocate a handle or picture and do need disposal. A claim verified for one kind doesn't transfer to a sibling call using a different kind constant without re-checking that kind's own branch.
15. **Do not assume a helper header's getter/setter names are symmetric, and do not assume every setter in the same header shares the same key-type overloads as its siblings.** A call like `ob_get_s(options, L"key", &value)` written to mirror an existing `ob_set_s(obj, L"key", value)` looks safe by naming convention alone, but the header may simply not define the "obvious" sibling name, or may not fully mirror it (e.g. the real getter might be named `ob_get_a` instead, or a numeric setter might declare only a wide-key overload while its string/bool siblings declare both). **Verify each getter/setter name, and each function's specific set of key-type overloads, against the actual header — treat "this sibling function probably exists/matches" as a hypothesis to check, not a fact to assume, even for a small in-house helper header.**
16. **A manifest's own syntax string can settle an exception-safety concern without needing to trace SDK internals at all.** A swallowed exception is a hang risk *if* the host is left waiting for a `PA_Return*` call that never happens — but only if the command is actually declared with a return value. A manifest syntax with no colon-plus-type-token after the closing paren settles, by the project's own documented convention, that the command has no return value and is fire-and-forget; a `catch(...)` swallowing an exception from its handler therefore cannot cause the hang failure mode, whatever else it might hide. **Always check the manifest's syntax string for a command before ranking an exception-swallow as a hang risk** — a one-line check that can close out or downgrade the finding immediately.
17. **A block comment documenting an intended precedence/priority order for mutually-exclusive options is a claim to verify against control flow, not just prose to relay.** The anti-pattern: a chain of independent `if` statements, each unconditionally assigning a shared variable when its own key is present, with no `else`. Every individual block looks correct in isolation — the bug only appears when checking the *set* of blocks against the documented intent, since whichever block is checked *last* silently wins if more than one key is present, the opposite of "first-documented takes priority." The fix is mechanical (`if`/`else if` in the documented order) once seen, but the bug is easy to miss reading one block at a time rather than checking the chain's aggregate precedence behavior.
18. **When a systemic bug (wrong identifier, wrong type, wrong overload) is fixed across every *live* call site, also grep the same file for the identical anti-pattern inside comments, `#if 0` blocks, or other dead code — but don't silently "fix" it and don't silently ignore it.** Dead code has no behavioral effect today, so rewriting it is scope creep; leaving it unmentioned means the next person who revives that feature reintroduces the exact bug just fixed elsewhere. Flag it explicitly by name — "same bug shape, currently inert because it's commented out, will resurface if this feature is ever revived."
19. **When a claim about a vendored library's runtime output shape would otherwise be asserted from reading its code alone, and that library's own source is available and buildable standalone (no proprietary SDK dependency required), build a small harness that links directly against its real `.c`/`.h` sources and run it against a real sample input** — don't reason about it from a recursive switch statement alone if you can just execute it. A harness that actually executes the real vendored code is a stronger source of truth than even a careful read of that same code, and building one is usually cheap relative to the risk of documenting (or fixing around) a wrong shape.
20. **A vendored C library's own `bool`-compatibility header can silently give C and C++ translation units two different layouts for the identical struct — check this explicitly whenever a struct containing a `bool` field is stack- or heap-allocated in `.cpp` code and passed by address into a function compiled from a `.c` file.** A header written to make a C library callable from both C and C++ often does `#ifndef __cplusplus` / `typedef int bool` / `#endif` — a C compilation gets an `int`-sized bool (4 bytes on most ABIs), while the same header in C++ falls through to the language's native 1-byte `bool`. If the library's `.c` files are compiled as C while the plugin's `.cpp` file declares the identical struct on its own stack before passing its address into a `.c`-compiled initializer, the two translation units disagree about that struct's size and field offsets — the C-compiled function writes past what the C++ caller's stack frame reserved, with no warning on either side. **Whenever a vendored C library is called from `.cpp` code and any struct crossing that boundary contains a `bool` (or `wchar_t`, the equivalent trap on macOS specifically), compile a `sizeof(...)` probe once as `.c` and once as `.cpp` against the unmodified header and compare, rather than assuming layout compatibility just because both sides share one header file.** Flag this as a finding to offer, not to fix silently — the standard fix (`#include <stdbool.h>`) is unverifiable here without a real rebuild on each shipped platform.
21. **Once a specific identifier-naming gap in a shared/vendored helper header has caused a CI failure in one project that uses it, treat that gap as a known landmine in *every other* project sharing the same header, and grep for it proactively during the initial code-review pass — before a build ever runs.** A header's own inline comments can be a tell here: gaps that carry a comment of the shape "confirmed live in this project's own CI: `<other-plugin>.cpp(line,col)`" indicate the maintainer patches reactively per-incident; a recurring gap with **no such comment** despite hitting multiple unrelated projects is worth reading as intentional (callers are expected to use the alternate name) rather than something likely to be "fixed" upstream — fix the call site, don't expect or file a header-side fix. Confirmed in practice: a project's `ob_get_s(options, L"key", &value)` calls (written to mirror an existing `ob_set_s`) failed CI with `error C3861: 'ob_get_s': identifier not found`; the vendored header's real getter was `ob_get_a`, carried no reactive "confirmed live in CI" comment the way nearby `ob_set_n`/`ob_set_0` gaps did, and renaming the call sites (not touching the header) cleared the build — exactly the outcome this rule predicts.
22. **A CI log's checkout step (exact repo/ref) or compiler invocation line can retroactively settle an *unrelated* open question left over from an earlier, separate code-review pass on the same source — not just the specific error currently being triaged.** Whenever either becomes knowable, treat it as an opportunity to close out every still-open, evidence-dependent claim from any earlier review of that same source, and state explicitly which prior open question got closed and how.
23. **Prefer a direct `raw.githubusercontent.com/<owner>/<repo>/<ref>/<path>` fetch over the GitHub Contents API (`api.github.com/repos/.../contents/...`) when the exact file path is already known.** The Contents API is convenient for *discovering* a path, but counts against GitHub's unauthenticated rate limit far more aggressively than raw file fetches. If the path is already known or guessable from the project's own conventional layout, go straight to the raw file URL; fall back to the Contents API only to discover an unknown path.
24. **When tracing an opaque SDK handle's lifetime across a function call, account for pass-by-value semantics before concluding *where* a dispose call would belong — but treat this as locating a candidate release point, not as proof one is actually needed.** A handle passed *by value* into a helper function gives that function its own local copy — reassigning that local parameter inside the callee does not retroactively change what the caller's own variable holds, so the caller's own scope is where a dispose call would belong if one is needed at all. This reasoning correctly identifies where to place a release call if the SDK's ownership model requires one — it does not by itself establish that it does; pair it with an explicit ownership check (§3) before inserting the call.
25. **When a CI log names an exact tag/ref, do not assume the source it built is whatever you last edited locally — fetch that exact tag and diff it against your local copy before trusting either as the basis for a root-cause claim.** Local edits live in the sandbox; the CI run checked out the real remote, which may or may not be byte-identical. State the diff result explicitly either way — "identical, so the fix isn't implicated" or "differs at X, so re-derive against what's actually there."
26. **When a CI failure's root cause isn't visible in the file that errors, and the project's git history is reachable, fetch the previous known-good tag alongside the current failing one and diff the whole tree — not just the file the error points at.** The actual regression can be in a vendored SDK header the erroring file merely `#include`s. A whole-tree diff between "last known good" and "first known bad" is a more direct route to root cause than reasoning forward from the error site alone, especially when the erroring file itself is unchanged between the two tags.
27. **Before treating a CI failure as a regression, check whether the failing platform/job has ever actually succeeded before** — a brand-new CI job exercising a code path for the first time can surface a bug that has been latent in the source indefinitely, and "regression" is the wrong frame for that. Two checkable signals settle this: the workflow YAML's own diff/comments between tags (a job section that's new), and the project's actual published release assets (if every prior release only ever attached one platform's binary, the other platform's build has never gone through CI before, regardless of how long the source itself has existed). This changes both the fix (patch the plugin's own source, no bisection of *recent* commits needed) and the framing (state plainly this isn't a regression from anything just changed).
28. **A fix that adds a previously-missing `#include` for a system/vendor header can itself introduce a new failure if that header has its own prerequisite headers, and the fix's placement doesn't guarantee those run first.** The fingerprint: if a fix advances past the original errors but a *system* header starts throwing paired "unknown override specifier" + "missing type specifier" errors on its own struct members, that's the signature of the header being parsed before its own prerequisite basic types were defined. **When adding an include to resolve a missing-declaration error, check whether the newly-added header has its own undocumented prerequisites, and satisfy them explicitly and locally** (leaning on the prerequisite's own include guard to make re-inclusion elsewhere harmless) rather than depending on include order that happens to work only by accident of what else is nearby.
29. **Before citing a freshly-fetched "upstream" file (a raw source, a vendored header at a specific commit) as independent confirmation of anything, check whether its content could only be explained by your own edits earlier in the same session.** A fetch that comes back byte-identical to your own already-patched local working copy — including custom comments or fix wording you personally wrote minutes earlier, which cannot legitimately exist on a real, independently-tagged upstream commit — is not corroboration; it's a sign the fetch itself is broken, mocked, or otherwise contaminated (a caching artifact, a sandboxed network path silently substituting local content, etc.), and folding it into a root-cause narrative launders your own guess as independent evidence. **Two concrete techniques settle this cheaply:**
	- **Run a quick control fetch of a well-known, unrelated file** (a stable public repo's README, a file you never touched) **before trusting a suspicious result** — if the control comes back correct and distinct while the file in question mirrors your own session, the network path itself is fine and the specific result is the problem, worth flagging plainly rather than silently trusting or silently discarding.
	- **Prefer evidence in the suspicious fetch that you did not personally originate** (an identifier, a function name, a piece of wording you never wrote yourself) over anything that overlaps your own edits — content you couldn't have contaminated by your own session is real corroboration even from an otherwise-untrustworthy fetch; content that matches your own wording isn't, no matter how convenient it looks. State this distinction explicitly to the user rather than quietly picking whichever version of the fetch supports the finding.
   - **When you have a local scratch copy of a file open for editing, a same-repo fetch of that exact filename is the specific one at risk** — the tooling can resolve a fetch for a path that collides with a file you're actively editing locally to your own working copy instead of the real remote. This is narrower than general fetch unreliability: the correct control isn't just any unrelated external repo, it's a **different filename in the same repo at the same commit**, one you've never edited (a `manifest.json`, a `README`, a config file). If that fetches clean and matches a pristine copy, the fetch mechanism itself is fine and the contamination is specific to the colliding filename — say so plainly, and avoid re-fetching that filename for verification purposes for the rest of the session (reasoning from the CI log and from differently-named files instead).
   Confirmed useful in practice: a vendored JSON-helper header fetched at the exact failing commit showed a getter genuinely named `ob_get_a` rather than the guessed-symmetric `ob_get_s` — a detail never present in any local edit, and therefore trustworthy corroboration for the identifier-rename fix — even though a companion fetch of the plugin's own `.cpp` at that same commit came back suspiciously identical to a locally-patched copy (because a local file of that exact name was being actively edited in the same session) and was called out as unreliable rather than cited. A same-repo fetch of `manifest.json` at that commit, a file never locally touched, came back byte-identical to the pristine original and confirmed the fetch path itself was sound.
30. **Grep every platform-gated system/vendor-library include (`gdiplus.h`, `<CoreGraphics/CoreGraphics.h>`, etc.) for actual use of its namespace/prefix (`Gdiplus::`, `CG...`) in the plugin's own source before treating the include as load-bearing.** 4D's Plugin Wizard template can leave a platform library `#include` and its linker pragma (`#pragma comment(lib, "gdiplus.lib")`) in the generated header even when the plugin's real implementation never calls into it — e.g. because the actual work is delegated to 4D's own internal commands via `PA_ExecuteCommandByID` instead of direct platform-API calls. An include confirmed unused this way is a strong candidate for outright removal (not just reordering or patching around) the moment it becomes a source of build fragility — see §5j.
31. **A downstream job's `needs:` chain in the workflow YAML settles whether it has ever had the chance to run, which is a stronger and cheaper signal than scanning historical run outcomes.** If job B declares `needs: [job A]` and job A has failed on every prior tag, job B failing on the first tag A finally succeeds on is not a regression in B — it's B's first real execution, full stop. Read the `needs:` graph before asking "did this job use to pass"; if it structurally couldn't have run before, that question has no meaningful answer and shouldn't be asked.
32. **When a fix that worked reappears as failed later with the byte-for-byte identical error signature, diff the current vendored artifact against the specific commit where it last passed — not just against the immediately preceding tag.** A regression can silently jump backward across several intermediate tags (a rebase, a merge from a stale branch, tagging the wrong commit) and land exactly on old, previously-diagnosed content. Confirm this by hashing/diffing the current file against both the last-known-bad and last-known-good copies: an exact match to the old bad copy (not merely "similar") is proof of reversion, not a new bug, and the fix is "restore the known-good file," not "re-diagnose from scratch."

## 3. Epistemic discipline — the most important non-mechanical rule

The single biggest quality risk in this kind of review is **asserting a resource leak or API misuse without having actually traced the ownership contract**, especially for an SDK whose internals weren't available at the time of the original claim.

**Apply this hierarchy of confidence to every claim in the review:**
- **Traced through the actual source, both call site and implementation** → state as fact.
- **Inferred from a well-documented, stable convention of the SDK/language** (e.g. general C++ exception propagation rules) → state as fact.
- **Settled by an explicit ownership doc comment** on the exact function used → state as fact, cite the comment.
- **Accepted on architectural-convention inference** (e.g. "a dedicated copy primitive exists elsewhere, so plain assignment must already share/transfer the handle by default") → a real, legitimate way to resolve a claim, but a different confidence tier than a directly-quoted comment — label it as inference, not certainty, and re-derive what accepting it implies for *other* nearby code paths (it can flip one path from "possible leak" to "confirmed no leak" while making a different path a more confident leak than before).
- **Plausible but not actually traced** → say so explicitly as an open question, and name what evidence would settle it, rather than asserting it either way.
- Never fill a gap in understanding with a confident-sounding guess dressed as a finding.

**A paired create/dispose (or retain/release) function existing in a header is a hypothesis worth raising, not a fact to act on by unilaterally inserting a release call** — especially for a resource explicitly documented as "manipulated by reference," where the SDK may do its own internal reference management invisibly from the header alone. Prefer surfacing the ownership question explicitly and asking, or confirming via an actual build/run if available, over silently adding a dispose call on inference — the cost of a wrong dispose call (a crash, potentially hard to reproduce) is worse than the cost of a leak that turns out to be real but goes unfixed for one more round. This applies even when the shape looks identical to a case that was previously settled correctly by an explicit comment — the presence of a paired dispose function is not itself the same evidence as a comment that actually states the ownership contract.

**When a person who plausibly has more context (they wrote the SDK, the plugin, or has compiled/tested it) disputes a specific technical claim, the correct response is neither reflexively agreeing without re-checking, nor defending the original claim from memory — it's re-deriving the claim from primary evidence and then stating plainly whether the original claim was wrong, and why, with the evidence shown.** Retracting a specific wrong claim doesn't mean retracting the rest of the review — other findings stand independently and should be reaffirmed as still open.

**Every time new source shows up in the conversation, check it against every hedge still open from earlier in the session — don't wait for the person to ask whether it changes anything, and don't let an unrelated immediate question crowd out the sweep.** Say explicitly which hedges got closed and which way they landed, even ones the person didn't ask about again.

**Treat a downstream confirmation (a later successful build/release, a person's own test) as closing the specific item it covers, and say so plainly** — distinct from, and stronger than, "I applied a fix I believe is correct." Scope this precisely: a green build for one platform confirms only what that platform's compiler actually parsed and linked. A platform-gated (`#if VERSIONMAC`/`#if VERSIONWIN`) fix living entirely inside the *other* platform's block is invisible to a build that never preprocessed it at all — state explicitly which fixes a given green build actually compiled versus which fixes it did nothing to verify.

**This same discipline extends to any externally-supplied "specification" text a user provides** (e.g. a claimed manifest.json syntax convention) — verify it against a primary, checkable source (the actual upstream SDK repo/README, a real sample file) before treating it as ground truth for anything written downstream, rather than deferring to it or to a majority-looks-right guess.

## 4. Fix workflow, once findings are agreed

1. **Present findings ranked by severity/impact**, each with: the exact code excerpt, why it's a problem (mechanism, not just "this is bad"), and a concrete fix direction. Freezes/hangs and crashes outrank leaks; leaks outrank latent-but-currently-safe bugs; those outrank purely theoretical/stylistic issues.
2. **Copy read-only uploaded files to a writable working directory** before editing (uploads mount is read-only in this environment) — never try to edit in place under the uploads path.
3. **Apply fixes incrementally, most-impactful first**, and re-view the file after each edit before making the next one.
4. **Check in with the user before applying invasive, hard-to-verify fixes** — especially ones that are platform-specific and can't be compile-tested in this environment. A single targeted question is the right amount of friction; don't ask permission for straightforward, clearly-scoped fixes the user already asked for.
5. **State compile-testing limitations honestly.** This environment cannot compile Windows/macOS/4D-plugin-SDK code. Every fix should be delivered as "a source-level fix, build and test before shipping" — not implied to be verified when it wasn't.
6. **Review your own patches as critically as the original code, before calling the work done.** Cross-check every new call against the actual declared signature of whatever helper it calls, especially helpers touched earlier in the same session — don't assume an edit is correct just because it compiles "in your head."
7. **Re-deliver the full corrected file(s) after each meaningful round of changes**, not a diff-only description, so the user always has a complete, current, buildable copy.
8. **If the person later says a previously-agreed fix "was never applied," diff their re-uploaded file against your own last-known-good working copy before re-deriving or re-explaining anything.** A direct `diff` pinpoints exactly what's missing and lets you patch precisely that gap rather than re-reviewing the whole file or assuming the earlier work was faulty.

## 5. Diagnosing CI/build-log failures (a distinct task shape)

Sometimes the input isn't source to review proactively, but a **failed CI build's log bundle** with an ask to "suggest a fix." This is a different task shape from §§1–4 — failure triage from a symptom, not auditing code for latent issues — but the same epistemic discipline (§3) applies: trace the actual root cause from evidence in the log, don't pattern-match to a plausible-sounding fix.

1. **Unzip and map the log bundle before reading anything closely.** CI log exports are typically one file per job/step. Find the step that actually failed (non-zero exit / `##[error]`) rather than assuming it's the last file alphabetically.
2. **Read the compiler invocation line itself**, not just the errors — it tells you the exact source files in the compilation unit, the include paths, and the preprocessor defines in force. Essential context for explaining *why* an error triggers on this project's specific build flags and not in general.
3. **Localize the failure to a specific translation unit by comparing which files succeeded vs. failed**, when several are compiled in the same invocation — this pinpoints whether the cause is "something included before a shared header, in this specific file's include chain" versus "something wrong with that header in general."
4. **Recognize known error signatures as a class, not just literally.** A cascade of struct-redefinition and undeclared-identifier errors inside a Windows SDK header, coming from `winsock2.h`/`ws2tcpip.h`, is a recognizable class of bug (legacy `winsock.h` vs. `winsock2.h` collision from `windows.h` being pulled in first) with a standard, well-documented fix (`WIN32_LEAN_AND_MEAN`), not something to improvise from first principles each time.
5. **Trace the actual include chain to explain *why*, not just *that*.** Walk the real chain: which header in this specific project plausibly pulls in the problem header ahead of the point where existing code already tries to order things correctly.
6. **Prefer a structural fix over a fragile reordering fix**, and say why. Reordering a specific `#include` to happen earlier "solves" the observed symptom but re-breaks silently the moment any dependency's internals change what it pulls in and when. A macro defined before the *first* include, fixing the underlying mechanism regardless of include order, is robust to future changes elsewhere in the chain.
7. **Name the residual risk of a structural fix explicitly.** A broad suppression macro can strip more than the one thing it was aimed at — state plainly what wasn't observed to need the stripped functionality, and that this can't be verified without an actual rebuild in this environment.
8. **When a structural fix needs to sit before the *first* include in the file — including before the SDK's own platform-detection header — don't gate it on that SDK's own platform macro** (e.g. `VERSIONWIN`/`VERSIONMAC`), since those are typically defined *by* that very header and aren't available yet at the point the fix needs to run. Use the compiler/platform's own predefined macro instead (`_WIN32`, `__APPLE__`/`__MACH__`) — always defined before any project header is reached, safe to branch on at the very top of the file.

### 5a. Vendored header/binary ABI mismatches (link-time, not compile-time)

Recognize on sight: `LNK2001`/`LNK1120` ("unresolved external symbol") on Windows, or `Undefined symbols for architecture ...` from `ld` on macOS, for ordinary methods of a vendored C++ dependency (assignment operators, `operator[]`, anything whose signature could plausibly have changed between releases) — not for anything project-specific.

**Diagnostic technique:**
1. **Recognize the signature.** Unresolved-symbol errors naming ordinary methods of a well-known vendored library — especially assignment operators, move-constructors, or anything that gained/lost an overload across major versions — is very often a header/binary version split, not a real missing dependency.
2. **Compare declared signature (header) against actual exported symbol (binary), not against library documentation or version numbers alone.** Version strings can lie or be stale; the binary's symbol table is ground truth. Without a native toolchain (`dumpbin`/`nm`), `strings` on the raw `.lib`/`.a` still surfaces mangled names — MSVC mangling encodes reference-vs-value in the parameter substring directly (`V01@` = pass-by-value, `AEBV01@` = const reference, `$$QEAV01@` = rvalue reference); Itanium (macOS/clang) mangling does the same (`aSERKS0_` = `operator=(const&)`, `aSEOS0_` = `operator=(&&)`). Matching or mismatching these substrings between header and binary settles the claim without compiling anything.
3. **When multiple platform binaries vendor the same header-only-versioned dependency, treat a one-platform fix as provisional until you've checked whether it touched shared files.** If headers are shared across platform targets, replacing one platform's binary to match the shared headers is fine; replacing the shared headers to match one platform's binary silently re-breaks every other platform that was previously fine. State this explicitly as a residual risk.
4. **Confirm whether a newly-surfaced issue is a regression or was always latent**, especially when a fix "reveals" a new failure — don't assume the new fix caused it. Diff or hash-compare the suspect files across the last-known-good and current tag. A pre-existing latent defect newly exposed (because an earlier, unrelated compile error previously failed the build one step sooner) is not something to hunt for in your own recent edits.
5. **A whole-header rollback (swapping in an entire older version of a vendored dependency's header, rather than patching one signature) is a legitimate fix when the header and the compiled binary genuinely come from different releases** — confirmed by comparing the exact mangled symbol the linker names against what each header generation would produce (MSVC: return-type substrings like `AEAV`/non-const-ref vs `AEBV`/const-ref, sitting right next to the const/non-const method-qualifier substring; Itanium: the mangled name doesn't encode return type at all, so cross-check via the overload count/constness instead). Concretely: `Value& deref() const;` (single overload) mangles to `?deref@ValueIteratorBase@Json@@IEBAAEAVValue@2@XZ`; `const Value& deref() const; Value& deref();` (two overloads, one dropped) produces a different symbol for the const one, `?deref@ValueIteratorBase@Json@@IEBAAEBVValue@2@XZ` — a one-character substring difference (`AEA` vs `AEB`) that fully explains an otherwise-mysterious `LNK2001`.
6. **Don't audit a large header-rollback diff line-by-line for every API surface change — let a full, clean compile-and-link of the actual consuming code be the verification.** A rollback across several jsoncpp releases can touch hundreds of lines (typedefs vs `using`, exception-class guards, template `as<T>()` helpers, move-constructor guards) that have nothing to do with the one symbol that was actually failing. The only surface that matters is what the plugin's own translation units actually call — a green build after the rollback confirms exactly that surface is fine; it says nothing about, and doesn't require auditing, the rest of the header's changed API that the plugin never touches.
7. **When the same header is shared across multiple platform build targets, each with its own separately-vendored binary of the same dependency, don't assume a fix for one platform's mismatch is risky for the other platform without checking that platform's own binary.** The shared-header risk (§5f) is real in general, but resolve it with evidence per platform, not by treating the risk as automatically materializing: extract the relevant mangled symbol from *each* platform's vendored binary independently (`strings` plus the platform's own mangling scheme) before concluding a shared-header change breaks or doesn't break the other side. In one real case, a header rolled back to fix Windows turned out to already match macOS's independently-vendored binary too — the two vendored binaries happened to be from compatible-enough eras even though only one platform's mismatch had actually surfaced yet.

### 5b. Assumed getter/setter symmetry and per-function key-overload mismatches (compile-time, `C3861`/`C2664` on an in-house helper header)

Recognize on sight: an "identifier not found" or a cascade of argument-conversion errors against calls to a project's own small JSON/object-helper header (as opposed to a large third-party SDK) — these read like typos or a one-off mistake, but are often a single systemic assumption applied consistently and wrong everywhere.

**Diagnostic technique:**
1. **Don't try to fix this from the error text or a plausible guess** — these headers are small enough that fetching or viewing the real declaration (at the exact ref a CI log's checkout step names, per §2.10) is nearly always cheap and available.
2. **When many call sites fail identically against the same function, treat it as one systemic root cause** (a wrong assumption about that function's overload set) rather than many separate mistakes — fix the pattern everywhere in one pass, and re-grep to confirm none were missed.
3. **A function's sibling in the same header is not obligated to share its overload set.** Seeing that one setter accepts both a narrow and wide key does not license assuming a nearby sibling does too — check each one.
4. **The compiler invocation line itself can retroactively close an "open question" left from an earlier code-review pass** — e.g. whether `/D _UNICODE /D UNICODE` are actually defined for this build, settling a previously-unverified assumption about wide-char handling. Read a CI log not just for the failure it reports, but for evidence that settles previously-open questions from an earlier pass on the same source.
5. **Fixing a missing-overload error by matching the *shape* of a working sibling call (e.g. "just add an `L` prefix") is only valid when the failing call site is itself a literal.** A call site built from a runtime value (e.g. a `std::string` constructed from parsed data, passed via `.c_str()`) needs an actual conversion, not a mechanical prefix — and if that conversion crosses a fixed-width type into a platform-variable-width type (`wchar_t` is 16-bit on Windows, 32-bit on macOS), the target width has to be verified on every platform the fix ships on, not just the one the CI log complains about. A tempting direct pointer cast between such types will silently corrupt data on whichever platform's width doesn't match, while compiling and appearing to work on the other; the correct fix widens each source code unit individually into the destination's native width.

### 5c. Empty/misconfigured signing secrets (shell-script-time, not compile- or link-time)

Distinct from compiler/linker failures against source or vendored binaries — this failure class occurs entirely inside a plain shell step, often before the actual compiler invocation ever runs, which matters for scoping: a CI failure here says nothing about the reviewed C++ source one way or the other.

**Diagnostic technique:**
1. **Recognize the signature.** A `security import`/`SecKeychainItemImport` decode failure, a `codesign` failure citing an empty or missing identity, or any step whose logged `env:` block shows a secret-sourced variable with nothing after the colon, is a credentials-configuration failure, not a code or build-script logic bug — don't start reading the shell script line-by-line looking for a scripting mistake first.
2. **Know how GitHub Actions actually masks secrets, and use it as a diagnostic signal.** A *populated* secret is always printed as `***` in the log — never in the clear. A variable that's genuinely blank after the colon tells you the secret evaluated to an empty string at the source, a stronger signal than inferring "probably a secrets problem" from the error text alone.
3. **Name the two live hypotheses without overclaiming which one it is**, unless the workflow YAML is available to check: the secret was never set (or was rotated and never re-added) under the exact name referenced, at whatever scope the job runs under; or a name mismatch between the workflow's reference and what's actually configured. Both produce the identical empty-variable symptom.
4. **Check "Secret source" and job trigger context as corroborating, not conclusive, evidence.** `Secret source: Actions` rules out one common cause (an unconfigured environment-scoped secret gate) but not a fork-PR context withholding secrets entirely.
5. **Scope the "no bearing on the source review" conclusion explicitly.** If the failing step precedes the actual compile step in the job's own step sequence, say plainly that the compiler/linker never ran and this failure is orthogonal to any previously-reviewed or previously-fixed source.

### 5d. A fix that hoists declarations/calls out of a `using namespace` directive's scope (compile-time, `C2065`/`C3861` against a vendored C++-namespaced C library)

This isn't a bug in the original source — it's a regression a reviewer's *own* exception-safety/cleanup fix can introduce, worth naming as its own class because the fix that caused it looks completely correct in isolation.

**Recognize the shape:** an exception-safety fix hoists a vendored library's handle variables from inside a nested block out to the enclosing function scope (so a wrapping `try/catch` can guarantee cleanup). If the library wraps its API in a C++ namespace (common for a C library wanting both C-linkage and namespace-scoped names — `namespace X { extern "C" { ... } }`) and the file's only `using namespace X;` directive lived inside that same nested block, hoisting the declarations moves them *outside* that directive's scope — a `using` directive's effect is lexically scoped to the block it's declared in, it doesn't retroactively apply to an enclosing scope. The result: a wall of "undeclared identifier"/"identifier not found" errors, all against identifiers belonging to one vendored library, appearing only on lines the fix just touched.

**Diagnostic technique:**
1. **Recognize the signature.** A wall of such errors, scoped only to lines a recent fix touched (not scattered through untouched code), is a namespace/scope regression from that fix — not a missing-include problem (a genuinely missing include produces errors on *every* use of the library, including untouched ones).
2. **Check whether the vendored library wraps its API in a C++ namespace even though it's a C library** — grep the vendored header for `namespace X` combined with `extern "C"`.
3. **Locate the file's `using namespace X;` directive(s) and check their lexical scope against every place `X`'s identifiers are now used**, especially any identifier the current fix moved to a wider scope than it lived in before.
4. **Prefer widening the `using namespace` directive's scope over qualifying individual call sites**, when every use of that namespace in the file is uniform — a single structural fix that covers every current and future use. Remove the now-redundant original directive.
5. **Extend self-review discipline to scope, not just signatures.** Whenever a fix hoists a declaration or call to an enclosing or sibling scope, explicitly check what that declaration's original scope was providing besides "being declared" — a `using namespace`, a `using` alias, a block-local `typedef`, or an `#if` region are all things that don't travel with a hoisted identifier automatically.

### 5e. Hardcoded per-developer dependency paths + a missing vendored binary (compile-time `C1083` today, link-time tomorrow)

A project-configuration failure class: an older `.vcxproj`'s `AdditionalIncludeDirectories` baking in a literal path under the *original developer's own user profile*, rather than an environment variable, a relative path, or a proper package-manager integration. A strong tell whenever a Windows CI job fails with `C1083: Cannot open include file` naming a third-party (not project-authored, not SDK) header — the CI runner's user account is never the same as the original author's, so the hardcoded path can never resolve there.

**Diagnostic/fix technique:**
1. **Recognize the signature.** `C1083` naming a well-known third-party library header, from a project old enough to predate a manifest-based package manager or a CI-provisioned dependency step, is very often a personal-machine path baked into project settings, not a genuinely absent dependency in the abstract.
2. **Grep the same project file for the *link-time* side of the same dependency before declaring the header fix complete.** `AdditionalDependencies`/`AdditionalLibraryDirectories` name the compiled library the header pairs with; check whether that file is actually vendored in the repo. If it isn't, the header-only fix will just move the failure forward to a link error on the next run.
3. **Prefer provisioning the dependency at the hardcoded path over editing the `.vcxproj`, when that path is repeated across every build configuration.** Installing the dependency at the exact path in CI resolves the include for every configuration with one self-contained step and zero project-file edits. Editing the `.vcxproj` to a portable property instead is the more durable long-term fix, but a larger change — offer it as an alternative rather than substituting it silently.
4. **Prefer discovering a dependency-manager-produced artifact's actual name/location over hardcoding a single guessed one.** A build-time search (`Get-ChildItem`/`find` a wildcard match against the actual install directory), with a loud failure plus a directory listing if nothing matches, finds whatever the tool actually produced instead of asserting a specific name or path that may not match across tool versions.
5. **An exhaustive, empty search is itself evidence, not a location still to find.** If a fully recursive search for a build artifact comes back with zero matches, that's evidence the artifact was never produced by this dependency snapshot at all — the fix belongs on the consumer side (the project setting that expects it, which may no longer need a compiled component at all) rather than a further path guess.
6. **Once one entry in a dependency/library list is confirmed phantom, check every other entry on the same list too, using evidence already available (an earlier compiler-invocation log, the project's own build history) rather than waiting for another failed run to reveal the next one.** A list wrong in one place, for an old project, is a reasonable place to expect it's wrong in more than one.
7. **When a compile error against a multi-component library clears one header only to fail on a different header from the same library, grep every file that actually gets compiled for every include from that library in one pass, and install/provision the complete resulting set together** — rather than resolving errors one at a time as each new missing header surfaces.

### 5f. Cross-platform builds sharing a symptom don't necessarily share a fix

When the same error text appears on a second platform/job in a cross-platform project, re-derive the fix from that platform's own project file and repo contents — don't port the first platform's fix over by pattern-matching on the error text alone. Two platforms can show the identical missing-header error while needing materially different fixes (e.g. one platform vendors a version-sensitive compiled binary and only needs matching headers; the other needs both, or neither) — the tell (a vendored binary already in the repo, a version number baked into a hardcoded path) is usually visible by inspection before running anything.

**When a library also has an already-vendored compiled binary in the repo, match headers to that binary's likely build version rather than defaulting to whatever a package manager's current snapshot provides.** A real compiled artifact has real ABI surface baked in from whatever version built it; mixing it with a different version's headers risks the header/binary ABI-split class in §5a — check version numbers in hardcoded paths, filenames, or comments and match as closely as possible, ideally by fetching the dependency's own source at that exact tagged version rather than a live current release.

**Cloning a multi-repo/submodule-split project's source is not the same as having its normal build output.** Some projects only expose a collated artifact (a unified header tree, a generated file) after running their own build/collation step on the raw checkout — check whether the artifact being reached for is something the checkout provides directly or something the project's own tooling produces, before assuming a simple copy from the clone will find it.

**When a generated/collated artifact is built from symlinks rather than real files** (common for tools that "collate" content from elsewhere rather than duplicating it), a plain recursive copy of only part of that artifact's source tree can produce dangling links if the links point outside what's being copied — a copy reporting zero errors is not evidence the destination is self-contained. Dereference (`-L`/`--dereference`) when relocating such a tree somewhere the original source won't be present.

**"Don't assume one platform's fix is safe/unsafe for the other" cuts both ways — verify, don't guess in either direction.** It's tempting to either port a fix blindly (assume shared risk is zero) or to withhold a clearly-needed fix out of caution (assume shared risk is certain) when a header is shared across platform targets. Neither is warranted without checking that platform's own vendored binary. Treat "does this break the other platform" as a checkable question (extract the relevant symbol from that platform's own binary) rather than a judgment call to hedge around.

### 5g. A vendored prebuilt binary that only covers one architecture of a multi-architecture build target (link-time, `symbol(s) not found for architecture <X>`)

A link-time **architecture** mismatch: an unresolved-symbols error naming ordinary symbols from a vendored library, specifically scoped to one architecture, on a build that explicitly targets multiple architectures (a "universal"/"fat" binary). Check this directly against the vendored binary's own contents (e.g. a Mach-O `cputype` field read from an extracted object file) rather than treating it as another path/provisioning gap to guess around — no CI-side path or version provisioning fixes a binary that was genuinely never built for the architecture being linked.

**When a fix's candidate resolutions differ in what the shipped artifact actually supports (not just in CI mechanics), that's a decision for the person, not an assumption to make on their behalf.** Building a real replacement binary for the missing architecture and dropping the missing architecture and relying on emulation/translation are both legitimate choices with real tradeoffs (native support and CI complexity/unverifiability vs. simplicity and reduced native compatibility) — surface the tradeoff explicitly rather than picking one unilaterally, even several rounds into a troubleshooting thread.

**When rebuilding or replacing a vendored artifact, derive its exact composition from the vendored artifact's own listing** (e.g. `ar t` against the real archive) rather than from external documentation or a plausible-sounding standard file set — verifying against the real file removes an otherwise-unnecessary uncertainty for free.

**When one vendored dependency is missing an architecture slice, check whether its siblings — the other vendored binaries checked in at the same location, for the same platform, presumably by the same person at the same time — already include it.** If three of four vendored libraries for a platform carry both required architectures and only one doesn't, that's strong evidence the outlier was simply never rebuilt when Apple Silicon (or whichever architecture) support was added elsewhere, not evidence of a project-wide vendoring policy gap. `lipo -info` (or `file` on a fetched copy) across the whole sibling set is a cheap way to confirm this and scope the fix to the one stale dependency rather than the whole vendoring approach. This also explains failure signatures that look like a scattered pile of unrelated missing symbols (`Value::~Value`, `CharReaderBuilder::newCharReader`, `ValueIteratorBase::name`, `ValueIteratorBase::deref`, ...) — when *every* symbol from one specific vendored library is missing for one specific architecture, that's "this whole library has no code for that architecture," not several distinct signature mismatches to diagnose individually.

**A fix that bypasses a library's own normal build system (compiling its sources directly with hand-picked flags instead of via its build tool) should be stated explicitly as unverified against a real toolchain**, with specific residual risk points named (e.g. whether a source file guarded by a feature macro compiles to the same effectively-empty unit without that feature's headers present) — a fix's own stated confidence should track how much of it has actually been run, not how plausible it reads.

**A decision surfaced as a call for the person can still change after they gain more context or capability than they had when asked — check what the original fix would now do to the new state of the world before assuming it stays.** If a person later takes on providing a real vendored artifact themselves, a CI step built to construct that same artifact becomes actively counterproductive (it can silently overwrite the hand-provided file on every run) — remove it cleanly rather than leaving it in place disabled.

**Once a dependency is being provisioned in CI specifically to satisfy a hardcoded path, vendoring that dependency into the repo and deleting the hardcoded path is a categorically stronger fix than continuing to provision it correctly.** It removes the entire class of future failure (version drift, a tool's output shape changing between runs, symlink/collation quirks, an upstream restructuring) that CI-side fetching is inherently exposed to, rather than just solving the current failure. Before adding any new search-path entry to point at a newly-vendored location, check whether an existing generic/wildcard entry already covers it — a redundant explicit entry is avoidable noise.

### 5h. A package manager's headers are not guaranteed behaviorally identical to the real upstream headers of the same nominal library and version (link-time, `LNK1104` naming a filename absent from every project setting)

A behavioral difference between two header sources both claiming to be "the same library," not a path/version/architecture mismatch. The signature: a "cannot open file" linker error naming an oddly specific decorated filename that appears **nowhere** in the project's own dependency settings — a strong tell the request isn't coming from the project at all, but from something the headers themselves are doing.

**A build succeeding against a package manager's vendored copy of a header-only-looking library does not confirm anything about how the real upstream headers of the same nominal version will behave.** Package managers routinely patch away compiler-specific mechanisms (MSVC's auto-link `#pragma comment(lib, ...)` embedded in a library's own headers is a classic example) for their own build-system convenience — a build that worked with zero explicit library dependency, using a package manager's headers, may simply never have triggered a mechanism the real upstream headers enable by default. Swapping to genuine upstream headers can reactivate exactly the thing that made the earlier build's silence deceptive rather than confirmatory.

**Treat a decorated, specific filename an auto-link-style mechanism requests as a literal, checkable clue, not a nuisance to blanket-suppress.** Such a name typically encodes the exact toolset generation, runtime, architecture, and library version the mechanism detected — read it before silencing it. Suppressing the mechanism entirely (a blanket "disable auto-link" macro) can clear the immediate linker error while trading it for a vaguer, later "unresolved external symbol" error once it turns out a genuinely compiled component actually was needed and nothing was providing it — suppression removes the mechanism that would have told the linker where to look, not the underlying need for the library. The more complete fix is usually to match what the encoded filename asks for (an official prebuilt binary for the toolset generation named, a build system pinned to match) and let the mechanism do its job, rather than suppress it.

### 5i. A recursive header-search wildcard silently promotes every vendored subdirectory to its own search root, and an old library's own compatibility shim can shadow real system headers as a result (compile-time, cascading errors deep inside system/standard-library headers with no obvious connection to the vendored dependency)

Not a missing header, missing binary, version mismatch, or auto-link quirk — a **name collision** created by the include-path setting itself. The most misleading symptom in this class: errors appearing entirely inside system/standard-library headers ("no member named X in namespace std", or errors deep in `<string>`/`<algorithm>`/`<complex>` internals), with nothing in the error text pointing at the vendored dependency at all.

**Recognize the mechanism.** A recursive header-search wildcard (e.g. `include/**`) doesn't just make a vendored tree reachable via its full relative paths — it adds *every subdirectory* under that tree as its own independent search root. If any vendored library ships an old-style compatibility shim whose files are deliberately named to match real standard-library header names with no extension (`cmath`, `cstdio`, `cstring` — meant to be found via a plain `#include <cmath>` on platforms whose C library once lacked certain functions), that subdirectory sitting on the search path can make the *standard library's own internal* unqualified includes resolve to the shim instead of the real system header, silently corrupting namespace visibility for the rest of the translation unit.

**Diagnostic technique:**
1. **Recognize the signature.** A wall of `std::`-namespace "no member named" errors originating *inside* system or standard-library headers — not the project's own files, not even the vendored dependency's normal headers — especially right after vendoring a large third-party header tree, is a strong tell for search-path shadowing.
2. **Grep the actual compiler invocation for the vendored tree's full search-path list, not just the project setting that generated it.** A single recursive wildcard setting can expand into hundreds of individual `-I` entries in the real compile line; any of those subdirectories could contain a file whose bare name shadows something the rest of the translation unit depends on.
3. **Check whether the recursive form is actually needed before assuming it must stay.** Grep every `#include` of the vendored library in the project's own source: if every occurrence uses the library's full root-relative form (never a shortened subdirectory-relative form), a single non-recursive search-path entry at the tree's root fully resolves them — the recursive wildcard was doing nothing the project's own code needed, only exposing every subdirectory (useful and dangerous alike) as an additional root.
4. **The fix is narrowing the search path, not patching the shadowed shim or defining a suppressing macro** — once step 3 confirms nothing needs the recursive form, switch to a plain non-recursive entry. This is more surgical than excluding one specific dangerous subdirectory (most build systems have no built-in per-subdirectory exclusion for a wildcard search path) or patching the vendored library's own shim file (which would need redoing on every future re-vendor).

**An existing generic/wildcard search-path entry already covering a newly-vendored location is necessary but not sufficient reason to leave it alone.** A *recursive* wildcard specifically should also be checked for what else it exposes once the vendored tree is large or old enough to contain files that shadow standard-library or system header names, not just for whether it resolves the includes intended.

### 5j. A header-reorder "fix" that's a complete no-op, because a different, earlier-included header already fully expanded the header being reordered (compile-time, a wall of "undeclared identifier"/"expected an expression instead of a type" errors inside a system library's own headers, e.g. `Gdiplus*.h`)

A fix that looks textbook-correct — "header A's own headers reference types declared by header B, so include B before A" — can have **zero effect on what the compiler actually parses**, because the file being edited isn't necessarily where header B is *first* pulled into the translation unit. If a different header, included earlier in the same `.cpp` (e.g. the SDK's own umbrella header, included before the plugin's own header), already does `#include <B>` unconditionally, then B's own include guard makes any *later* `#include <B>` — including the reordered one — expand to nothing. The relative order of two lines within the file you're editing is irrelevant if one of them was already resolved earlier via a completely different file.

**Recognize the signature:** a second CI run, built from source that has genuinely been confirmed (by diff against the exact tag) to contain the reorder fix, reproduces the **identical** error signature — same files, same line/column numbers, same error count — as the original failure. This is not weak or ambiguous evidence that the fix "might not have worked" — an exact byte-for-byte repeat of a multi-hundred-error signature, from confirmed-patched source, is direct proof the fix changed nothing about what the compiler saw.

**Diagnostic technique:**
1. **Before re-theorizing why a fix didn't work, rule out "the fix was never applied" first** — fetch the exact tag/commit that was actually built and diff it against your patched copy. If it's identical (mind CRLF/LF differences, which can make a real match look like a diff at first pass — normalize line endings before concluding either way), the fix genuinely landed and the *theory behind it* is what's wrong, not the mechanics of applying it.
2. **Once the fix is confirmed applied but ineffective, trace the header's real *first* occurrence across the whole translation unit** — not just the two lines that got reordered. Check every header included *before* the file you edited (especially an SDK's own umbrella header, if the plugin includes it first) for an unconditional or near-unconditional `#include` of the same system header. A per-translation-unit include guard means only the *first* inclusion's surrounding macro state matters; every subsequent `#include` of the same header, anywhere else in the file, is inert.
3. **Check the earlier-included header's own comments for explicit guidance on this exact situation.** An SDK header author who has hit this class of problem before may have left a direct, first-party note — e.g. `// some external libraries assume first load; include this file after them` — immediately above their own system-header include. That's authoritative, project-specific evidence about the required include order for a downstream library, and should be checked before reasoning about generic C/C++ prerequisite order from first principles.
4. **When the reordering theory is falsified, and the library in question was already confirmed unused elsewhere in the plugin's own code (§2.30), prefer removing the dependency entirely over continuing to iterate on an untestable load-order theory** — especially when the review environment has no matching toolchain (no Windows/MSVC, no macOS/Xcode) to compile-test a further reordering guess before shipping it as the "fix." Removing an unused dependency is a fix whose correctness doesn't depend on correctly guessing an SDK's internal header interactions; a further reorder attempt is another unverified guess of the same kind that just failed.
5. **State plainly that the earlier fix was wrong, and why — don't just apply the correction silently.** The person built and ran the earlier "fix" in good faith; retracting it explicitly (with the evidence: the identical error signature, the confirmed-applied diff) is more useful to them than quietly moving on to a different approach without saying the first one didn't hold up.

### 5k. A vendored library's own build system can name an "obvious" target that produces nothing linkable, and the project's own packaging convention may not match anything that build system actually outputs (CMake `OBJECT` libraries vs. their `STATIC` wrapper targets, `LNK1181`/no archive produced)

A build-from-source replacement for a missing/unbuildable prebuilt dependency can fail silently in a specific way: the CI step "succeeds" (no compiler error) but produces no archive file at all, because the target it built was never meant to produce one.

**Recognize the shape.** CMake's `add_library(<name> OBJECT ...)` compiles sources into object files but — on every generator, Visual Studio and Xcode included — never runs an archiver step. If a project's own naming convention for a vendored dependency (e.g. a `_OBJLIB`-suffixed filename baked into a `.vcxproj`/`.xcodeproj`, or referenced in a hand-maintained release asset list) happens to match the vendored library's own CMake *object*-library target name, building exactly that target by name will compile cleanly and produce nothing to link against — a `cannot open input file` or `LNK1181`-class error with no compile-time error preceding it.

**Diagnostic technique:**
1. **Don't assume a target name that "sounds right" is the one that produces a real artifact — check by building it and looking at the actual output directory**, rather than reading the vendored `CMakeLists.txt` and inferring. An `OBJECT` library and its `STATIC` (or `SHARED`) wrapper are often defined right next to each other in the same file, with the wrapper simply doing `add_library(<Name> STATIC $<TARGET_OBJECTS:<Name>_OBJLIB>)` — the *plain*-named target is very often the one that yields a real archive, while the suffixed one is the intermediate.
2. **When a project's own packaging convention (a specific filename it expects) doesn't match any target name the vendored build system documents, don't assume the convention is simply wrong — check whether it's a rename applied by whoever originally built and packaged the dependency**, rather than something the build system itself produces under that name. Confirm by building the plain-named target and checking whether its output, renamed, is what the convention expects.
3. **Building one "top-level" target by name can cascade-build everything it depends on in a single invocation**, if the vendored project wires dependencies via `target_link_libraries`/object-library composition — check for this before assuming every dependency needs its own separate build invocation.

### 5l. A documented CMake variable/policy mechanism silently not taking effect is often an execution-order problem relative to `project()`/`enable_language()`, not a wrong invocation — verify by reading the platform module's own source, not by re-trying the same mechanism differently

Recognize on sight: a fix that sets a well-documented CMake cache variable (or forces a policy default) produces a link/compile failure that is **byte-for-byte identical** to the failure before the fix — not merely similar, not partially improved. That exactness is itself diagnostic: it means the fix's mechanism never took effect at all, not that it took effect incorrectly.

**Diagnostic technique:**
1. **Don't reapply the same class of fix a second time with a different delivery mechanism (e.g. switching from a `-D` command-line flag to the same variable set inside a `-C` preload script) before checking *why* it had zero effect the first time.** A preload script (`-C`) runs before the project's own `project()`/`enable_language()` calls; a variable whose real population only happens *inside* that call (platform-specific compiler-flag defaults are the common case) is still empty at the moment a preload script tries to modify it, and forcing it to a cache value at that point can suppress the normal population entirely rather than override it.
2. **When a documented variable's effect depends on a policy (`CMPxxxx`), check the platform/generator module's own source for the exact `cmake_policy(GET ...)` branch that reads it**, rather than trusting that setting the policy's cache default is sufficient — the specific conditional structure (what populates the default when the policy is `NEW` vs. `OLD`) explains failures that reasoning from the documented *intent* of the policy alone won't.
3. **Once you understand *why* a variable-based approach isn't taking effect at the right time, a two-pass configure (let the normal population happen first, then reconfigure the existing build tree with a script that edits the now-genuinely-populated cache values) is a reliable fallback** that doesn't depend on getting execution-order-sensitive policy/variable interactions right on the first attempt.

### 5m. A CMake directory-scoped property set from a `-C` preload script does not propagate into `add_subdirectory()`-included targets — confirmed empirically, not by re-reading documentation a third time

A specific, narrower case of §5l's general lesson, worth calling out on its own because the failure mode looks identical to a naming or scoping mistake rather than a fundamental limitation of the mechanism chosen.

**Recognize the shape:** a `-C` preload script calls a directory-scoped command (e.g. `add_compile_definitions(...)`) intended to apply build-wide; the script loads without error (`loading initial cache file ...` in the log), yet a target added later via `add_subdirectory()` behaves exactly as if the command was never called.

**Diagnostic technique:**
1. **After two failed attempts at the same class of fix via different CMake mechanisms, stop guessing a third variant and build a minimal local reproduction instead**, even without the target project's exact toolchain. A tiny `project()` + `add_subdirectory()` + one source file, configured with the exact same `-C` script and command under test, settles definitively whether the mechanism propagates the way documentation implies — this is cheap to build and removes an entire category of continued guessing.
2. **Once a specific CMake mechanism is confirmed not to do what's needed, don't look for a fourth CMake-variable-based workaround** — consider whether the goal (a small, targeted change to how a vendored dependency compiles) is more reliably achieved by patching the vendored source text directly in the ephemeral CI checkout, which sidesteps the entire class of variable-propagation/scoping uncertainty. State plainly that this is a change in approach, and why the previous class of approach was abandoned rather than merely iterated on again.

### 5n. Recognize a whole family of bugs, not isolated incidents, when old vendored code encodes a since-invalidated platform assumption in a still-true macro — and check the *whole* vendored tree for repeats the moment you find one

Some vendored-library bugs aren't isolated typos; they're one assumption, written once at a time when it was safe, now silently wrong everywhere it appears, because the platform macro it guards on has changed meaning (or scope) since the code was written. `TARGET_OS_MAC` is a concrete example: it's unconditionally true on **every** modern Apple platform (macOS, iOS, etc.), but decades-old vendored code frequently uses it to mean specifically "classic, pre-OS X Mac OS" — assuming a header that no longer exists (`<fp.h>`), a function that didn't exist then but does now (`fdopen`), or a typedef the system was assumed to already provide (and now doesn't). The same wrong assumption can manifest as three structurally different symptoms (a macro collision, a missing header, an undefined identifier) depending on which specific thing the code assumed.

**Diagnostic technique:**
1. **Once you've found and fixed one instance of "this old vendored code assumes X about a platform macro that's no longer true," immediately grep the *entire* vendored tree for the same guard condition** (not just the one file that just failed) — before shipping the fix. Old, widely-copied library code (a decompression module, a compatibility shim) is very often vendored **more than once** by different dependencies in the same build (e.g. one library's own copy of zlib, and a second, independent copy the same build also pulls in via a different dependency's bundled sources) — fixing only the copy that happened to fail first just defers the identical failure to whichever copy compiles next.
2. **Expect the same root assumption to produce different-looking errors in different files** — don't assume a new, differently-worded error a build reaches after an earlier fix is an unrelated new bug before checking whether it's the same platform-macro assumption manifesting as a different symptom (missing header vs. undefined identifier vs. macro-expansion collision).
3. **Before deleting or unconditionally-defining something inside an old compatibility block, check what every *other* macro in the same guard condition means today** — if they're all equally obsolete (long-dead compiler/toolchain identifiers that can never be true on any build actually being run), the safe fix is usually removing just the still-live macro from the condition (or removing the guard entirely), not rewriting the whole block's logic.
4. **A one-line, targeted source patch applied to a fresh, ephemeral CI checkout (not a change to the person's own repository) is a legitimate and often lower-risk fix for this class of bug** — especially after a CMake-variable-based workaround has already been tried and shown not to propagate correctly (§5m). State clearly in the patch's own comment what the removed/patched condition assumed, why it's safe on every platform actually being built, and how the blast radius was checked (what else was grepped, and came back empty).

### 5o. Before treating any CI failure as a regression from a recent fix, confirm what was actually built by reading the checkout step's own ref/tag — not by assuming the newest source ran

A failure that reproduces an error from many rounds ago, in a project that has since been fixed for that exact error, is not evidence the earlier fix was undone — it's usually evidence a different, older piece of source got built. `workflow_dispatch` (or any manually-triggered run against a named tag/ref) is a common way for this to happen: a typo in the tag input (a stray leading/trailing space, an old tag reused by habit) silently checks out ancient source and an ancient copy of the workflow file itself, with none of the intervening fixes present.

**Diagnostic technique:**
1. **Read the checkout step's logged `ref:` value directly before attributing any failure to a recent change** — it's cheap, appears in every log, and settles the question immediately. A stray character in the ref (visible as unexpected spacing in the log's own `##[group]` line) is a strong, specific tell.
2. **Cross-check the failing error against the project's own known history** — if the exact same error, at the exact same line, was already fixed and confirmed in a later tag, the current failure is near-certainly a wrong-tag rerun rather than a regression, and should be named as such plainly rather than re-diagnosed as if it were new.
3. **When someone reports "you broke it" based on a failing build, treat the report as a request to investigate, not as confirmed fact about cause** — check the evidence (the ref actually built) before either agreeing or defending the fix; both a silent cave-in and a defensive re-explanation of the fix are worse than just pointing at the actual tag in the log.

### 5p. A CI-side compiler-version override that only touches `PlatformToolset` leaves whole-program-optimization settings pointed at the old toolset's vendored binaries (link-time, MSVC `C1047`/`LTCG:incremental`, "was created by a different version of the compiler")

Recognize on sight: `LINK : fatal error C1047: The object or library file '...' was created by a different version of the compiler than other objects like '...'; rebuild all objects and libraries with the same compiler`, immediately preceded in the log by the linker auto-detecting `/GL` content in a vendored library and announcing it's restarting the link with `/LTCG` — that auto-restart line is itself the tell that whole-program optimization is active and about to hit a version boundary.

**Recognize the shape:** a project's `.vcxproj` hardcodes both an older `PlatformToolset` (e.g. `v140`) and `WholeProgramOptimization=true` (i.e. `/GL` + `/LTCG`) for Release, matched to whatever toolset the vendored static libraries were actually built with. A CI job running on a modern hosted runner overrides `PlatformToolset` on the command line (because the old toolset component isn't installed) but doesn't touch `WholeProgramOptimization` — so the plugin's own sources compile fresh with the new toolset while `/GL`/`/LTCG` stays on, and the vendored libraries remain built with the old one. LTCG's intermediate object format is compiler-version-specific; mixing generations under LTCG is exactly what `C1047` reports.

**Diagnostic technique:**
1. **Check the project file itself for `WholeProgramOptimization` and `PlatformToolset` side by side** — if CI overrides one but not the other, and the vendored libraries are older than the overridden toolset, that mismatch is the mechanism, not a coincidence.
2. **The fix that matches the existing pattern is to add the missing override on the same command line** (`/p:WholeProgramOptimization=false`), exactly like the `PlatformToolset`/`WindowsTargetPlatformVersion` overrides already there for the same "old toolchain not available on this runner" reason. This is a one-line, low-risk change with a known, explicit cost (the CI-built Release binary loses whole-program optimization), not a correctness risk — call out that cost plainly rather than silently accepting or hiding it.
3. **Don't treat this as the same class of fix as rebuilding a vendored binary (§5a/§5g).** No vendored artifact needs to change; the fix is purely a build-flag decision, verifiable by nothing more than a clean CI run.
4. **This failure can also clear on its own without ever being diagnosed, if a later, unrelated linker error (e.g. an actual missing symbol) already fails the build first** — check the log's error ordering before assuming a fix for a *different* class of error also resolved this one.

## 6. What NOT to do

- Don't rank a theoretical/edge-case issue (e.g. a `>2GB` size truncation) alongside a freeze-causing bug — severity ordering is itself part of the deliverable's value.
- Don't silently "fix" something the user disputed without re-deriving it from evidence first — retract explicitly, with the evidence, or hold your ground explicitly, with the evidence. Never just capitulate to social pressure alone, and never simply repeat the original claim without addressing the counter-evidence.
- Don't invent SDK behavior to fill a gap — say "I don't know, here's what would settle it" instead.
- Don't treat a pasted "specification" from the user as automatically authoritative, especially if it's internally inconsistent or contradicts a primary source you can check.
- Don't claim a fix is verified/compiled when the environment can't actually compile it — say so.
- Don't flag a missing Linux code path in a 4D plugin as a finding — 4D has no Linux runtime, so `VERSIONMAC`/`VERSIONWIN`-only branching is complete by design, not an omission.
- Don't treat a single validation pass on a user-supplied numeric value as covering every downstream consumer of that value — check each system API it's later passed to for its own native parameter width (§2.12).
- Don't verify a third-party API claim against a dependency's upstream `master`/latest release and stop there — if a CI log or checkout step names an exact tag/ref, re-check against that ref specifically; a project can vendor an older or newer snapshot than current upstream.
- Don't fix a header/binary mismatch by changing the header (or the binary) alone when that header is shared across multiple platform targets — check what else links against it before declaring the fix complete, and say so explicitly if you can't check every platform from the current environment.
- Don't start hunting for a scripting or source-code mistake before checking whether a CI failure's logged `env:` block shows an empty (not `***`-masked) secret-sourced variable — that signature means a credentials/secrets-configuration problem, not a bug in the script or the reviewed source, and it's diagnosable directly from the log without guessing.
- Don't let a CI failure that occurred *before* the compile step run cast unstated doubt on source fixes made in an earlier session — check the job's own step sequence to confirm whether the compiler/linker was ever reached, and say plainly when it wasn't.
- Don't hoist a declaration or call out of a nested block (e.g. for an exception-safety/cleanup fix) without checking whether that block also supplied a `using namespace`, a local `using` alias, a block-local `typedef`, or similar scoped context the hoisted code was silently relying on.
- Don't read a green CI build as validating every fix applied in the same session when the source is split across `#if VERSIONMAC`/`#if VERSIONWIN` (or similar) — a build for one platform never even preprocesses the other platform's guarded block; state explicitly which fixes actually sat in the translation unit that build compiled, and which live entirely behind the untested platform's `#if` and remain unconfirmed.
- Don't insert a dispose/release call on shape-based inference alone (a paired create/dispose function existing, a "manipulated by reference" comment, a naming convention) without either an explicit ownership doc comment or actual confirmation — a wrongly-added release call can crash, which is a worse outcome than leaving a merely-suspected leak unconfirmed and flagged as an open question instead.
- Don't treat a third-party-header `C1083`/`file not found` CI error as a genuinely-unprovisioned dependency without first checking the project's own build settings for a hardcoded per-developer path — and don't declare that fix complete without also checking the dependency's link-time side and confirming the referenced binary actually exists in the repo (§5e).
- Don't respond to a search-for-an-artifact step coming back completely empty by guessing yet another specific location — an exhaustive, empty recursive search is evidence the artifact was never produced by that dependency snapshot at all, and the fix belongs on the consumer side, not in a further path guess (§5e).
- Don't stop checking a dependency list after fixing the one entry currently causing the failure — once one entry is shown to be phantom, check every other entry on the same list against evidence already available before calling the fix complete (§5e).
- Don't port a first platform's fix to a second platform showing the identical error text — re-derive it from that platform's own project file and repo contents first, since a hardcoded-path symptom that looks the same can hide a materially different underlying shape (§5f).
- Don't decide unilaterally between two fixes that differ in what the shipped artifact actually is or supports (e.g. dropping a target architecture vs. rebuilding a dependency to support it) — that's a call for the person, surfaced explicitly with the real tradeoff (§5g).
- Don't assume a vendored binary's exact composition from external documentation or a "standard" file list — read the vendored archive's own member/symbol listing and match against that (§5g).
- Don't keep maintaining a CI-side fetch/build step to satisfy a hardcoded personal path without also considering whether vendoring the dependency and deleting the hardcoded path is available and preferable (§5g).
- Don't treat a build that succeeded against a package manager's vendored headers as confirmation of how the real upstream headers of the same nominal library/version will behave — a linker error naming a decorated filename absent from the project's own settings is the signature of a compiler-embedded mechanism the package manager was silently suppressing, not a new dependency requirement (§5h).
- Don't treat suppressing a compiler-embedded auto-request mechanism as a complete fix just because it clears the immediate error — a decorated, specific filename it requests is a literal clue about what's actually needed; read it before silencing it (§5h).
- Don't assume a cascade of `std::`-namespace "no member named" errors originating inside system/standard-library headers is a toolchain problem unrelated to a recently-vendored dependency — grep the actual compiler invocation's full search-path list for a vendored subdirectory shadowing a real header name before assuming otherwise (§5i).
- Don't praise a generic/wildcard search-path entry as pure upside just because it happens to cover a newly-vendored location — a recursive wildcard specifically also exposes every subdirectory as its own independent search root, which can become actively harmful once the vendored tree is large or old enough to contain shadow-named files (§5i).
- Don't assume a vendored library's build-system target with a name matching the project's own packaging convention (e.g. an `_OBJLIB`-suffixed filename) is the one that produces a real linkable archive — an `OBJECT` library target compiles but never archives, on any generator; check by building it and looking at the actual output, not by reading the name (§5k).
- Don't retry the same class of CMake-variable-based fix a second time with a different delivery mechanism (a `-C` script instead of a `-D` flag, or vice versa) before checking why the first attempt had zero effect — a byte-for-byte-identical repeated failure means the mechanism never took effect, and the platform module's own source (not the variable's documented intent) explains why (§5l).
- Don't keep inventing new CMake-variable-based workarounds after a directory-scoped property set from a `-C` preload script is shown not to propagate into `add_subdirectory()`-included targets — build a minimal local reproduction to confirm the limitation once, then switch approach (e.g. patching the vendored source text directly) rather than trying a third or fourth variant of the same mechanism (§5m).
- Don't treat a newly-vendored-source build failure as an isolated, one-off bug the moment you've fixed one instance of an old platform-macro assumption (e.g. `TARGET_OS_MAC` meaning "classic Mac OS") — grep the whole vendored tree for the same guard condition before calling the fix complete; the same library is often vendored more than once by different dependencies in the same build (§5n).
- Don't assume a differently-worded error surfacing later in the same build, after fixing one instance of a platform-macro assumption, is an unrelated new bug before checking whether it's the same root assumption manifesting as a different symptom (§5n).
- Don't attribute a CI failure to a recent fix being undone without first reading the checkout step's own logged ref/tag — a manually-triggered run against a mistyped or stale tag will reproduce old, already-fixed errors and silently rebuild ancient source, including an ancient copy of the workflow file itself (§5o).
- Don't treat a report that a fix "broke" something as confirmed fact about cause before checking the evidence yourself — neither silently capitulating nor defensively re-explaining the fix is as useful as pointing at what the log actually shows was built (§5o).
- Don't treat a person's verbal report that a build "succeeded" as equivalent to primary evidence when it's the sole basis for closing out an explicitly-flagged unverified guess — an actual CI log takes precedence if it later contradicts the report.
- Don't reuse an earlier fetch of a project's source/workflow file as still-current without diffing any newly user-uploaded copy of "the same" file against it (and against the exact CI-log-named tag, if different) to confirm they agree.
- Don't cite a freshly-fetched "upstream" file as independent confirmation without first checking whether its content could only be explained by your own edits earlier in the session — a byte-identical match to your own already-patched working copy, down to custom wording you wrote yourself, means the fetch is compromised, not corroborating; run a control fetch of an unrelated known file to isolate whether the network path itself is fine, and say so plainly to the user rather than folding a contaminated fetch into the root-cause narrative (§2.29).

## 7. Checklist for the code-review half

- [ ] Full dispatch table read from `PluginMain`'s `switch(selector)`, not inferred from comments or the manifest.
- [ ] Every dispatched function read end to end, including all platform branches, not just its signature.
- [ ] Every SDK-provided handle's ownership/lifetime traced from creation to disposal before any leak claim.
- [ ] SDK function semantics verified against actual header/implementation, not assumed from the name.
- [ ] Exception-safety across the plugin/host boundary checked, distinguishing a hang risk (unreturned `PA_Return*`) from a plain crash.
- [ ] Platform-specific data-format handling checked for correctness (e.g. real palette resolution), not just presence of a code path.
- [ ] Latent-but-currently-safe uninitialized-variable patterns flagged even when not currently reachable.
- [ ] Hand-built narrow/wide string conversions checked for null-byte miscounts even when currently working.
- [ ] Theoretical-only issues (e.g. multi-gigabyte-scale truncations) not ranked alongside live freeze/crash risks.
- [ ] Third-party API claims checked against the project's own vendored copy at the exact tag/commit, not just upstream `master`.
- [ ] Any 4D-supplied numeric value used to size an allocation validated (finite, non-negative, explicit upper bound) before being cast to an unsigned/size type.
- [ ] A validated numeric value re-checked against the native parameter width of every other system API it's later passed to.
- [ ] Per-call open/close of an OS handle or provider in a hot-path command flagged as a performance finding, with a stateless/handle-free platform alternative checked for and preferred when one exists.
- [ ] No Linux-support gap raised as a finding.
- [ ] A "no need to clear/dispose" claim checked against the SDK factory function's own implementation for the specific kind constant used at the call site, not assumed uniform across every kind it can construct.
- [ ] A getter/setter name or overload set assumed by naming-convention symmetry verified directly against the actual header before being relied on.
- [ ] Every entry in a dependency/library list checked once any single entry is shown to be phantom, not just the one under investigation.
- [ ] (CI triage) The failing step identified by exit code/`##[error]`, not assumed to be the last file.
- [ ] (CI triage) The compiler invocation line itself read for source files, include paths, and preprocessor defines in force.
- [ ] (CI triage) A known error-signature class named explicitly (e.g. `winsock.h`/`winsock2.h` collision) rather than improvised from scratch, with the actual include chain traced to explain why it triggers in this project specifically.
- [ ] (CI triage) A structural fix preferred over a fragile reorder, with any residual/untested risk of that fix stated explicitly.
- [ ] Link-time "unresolved external symbol" errors for ordinary vendored-library methods checked as a possible header/binary ABI version split (declared signature vs. actual exported symbol) rather than assumed to be a missing-dependency or path problem.
- [ ] When a header is shared across multiple platform build targets, a fix that changes that header (or replaces one platform's binary to match a changed header) checked against every other platform target that shares it before being called complete.
- [ ] When a fix "reveals" a new failure further down the build, checked whether that failure was actually latent all along before treating it as a regression introduced by the fix.
- [ ] A CI failure's logged `env:` block checked for an empty (not `***`-masked) secret-sourced variable before any scripting or source-level explanation is sought.
- [ ] A failing step's position in the job's own step sequence checked against where the compile/link step actually runs, and stated explicitly if the failure precedes it.
- [ ] A downstream build-success report scoped precisely against what that job actually covers before treating it as closing every open compile-testing hedge.
- [ ] Any own-fix that hoists a declaration or call to an enclosing/sibling scope checked against that original scope's `using namespace`/`using`/`typedef`/`#if` context.
- [ ] A build success for one platform not read as validating a fix living entirely inside the other platform's `#if` guard.
- [ ] When a CI log names an exact tag/ref, that tag fetched and diffed against any local copy already in the session before attributing the failure to (or clearing) any local edit.
- [ ] When the erroring file itself hasn't changed between a known-good and known-bad tag, the whole tree diffed between those tags, not just the erroring file.
- [ ] Before writing up a CI failure as a regression, the failing job's own presence in past passing runs checked (workflow YAML diff, published release assets).
- [ ] After adding a `#include` to fix an "identifier not found" error, checked whether the newly-added header has its own prerequisite headers and whether the fix's placement guarantees those ran first.
- [ ] A third-party-header `C1083`/`file not found` error checked against build settings for a hardcoded per-developer path before assuming the dependency is genuinely unprovisioned — and the same file checked for the dependency's link-time side, with the referenced binary's presence in the repo confirmed.
- [ ] A dependency-manager-produced artifact's filename/location discovered at build time (a wildcard search with a loud failure and directory listing if not found) rather than hardcoded as a single guess.
- [ ] An exhaustive, empty search for a build artifact treated as evidence the artifact doesn't exist in this dependency snapshot, with the fix redirected to the consumer rather than a further path guess.
- [ ] When a compile error against a multi-component library clears one header only to fail on a different header from the same library, every compiled file grepped for every include from that library in one pass, with the complete resulting list provisioned together.
- [ ] When a second platform/job surfaces the same-looking error as an already-fixed platform, that platform's own project file and repo contents checked directly before porting the first fix over.
- [ ] Before installing "current"/"latest" headers for a library that also has an already-vendored compiled binary, the binary's likely build version checked and matched as closely as possible.
- [ ] Before assuming a raw clone of a multi-repo/submodule-split project contains the same unified artifact its normal build produces, checked whether that artifact requires the project's own build/collation step first.
- [ ] When a generated/collated artifact is built from symlinks, a recursive copy of only part of its source tree checked for links pointing outside what's being copied, and dereferenced before relocating.
- [ ] A link-time "symbol(s) not found for architecture X" error against a vendored prebuilt binary checked directly against that binary's own contents before assuming a CI-side provisioning fix applies.
- [ ] When a fix's candidate resolutions differ in what the shipped artifact actually supports, the tradeoff surfaced explicitly to the person as a choice.
- [ ] When rebuilding or replacing a vendored compiled artifact, its exact source-file composition derived from the vendored artifact's own listing, with any fix bypassing the library's own build system stated explicitly as unverified.
- [ ] Whenever a CI step exists solely to provision a dependency at a hardcoded personal path, considered explicitly whether vendoring that dependency and deleting the hardcoded path is available and preferable.
- [ ] Before adding any new include/search-path entry to point at a newly-vendored location, existing settings checked for an already-generic entry that covers it without modification.
- [ ] A link-time "cannot open file" error naming a filename absent from every explicit dependency list checked as a possible compiler-embedded auto-link request before assuming it's a missing entry to add back.
- [ ] When switching from a package manager's vendored copy of a library to the real upstream headers, a previously-green build treated as evidence of that specific vendored copy's behavior, not of the real library's behavior.
- [ ] Before suppressing a compiler-embedded auto-link (or similar) mechanism, the specific requested filename/identifier read for what it encodes, and checked against what's actually available, before silencing the mechanism.
- [ ] A cascade of `std::`-namespace "no member named" errors inside system/standard-library headers checked against the actual compiler invocation's full search-path list for a vendored subdirectory shadowing a real header name.
- [ ] Before leaving a recursive header-search wildcard in place, every `#include` of the vendored library checked for whether it actually needs the recursive form, narrowing to a non-recursive entry if not.
- [ ] A vendored build system's target name matching the project's own packaging convention verified by actually building it and checking the output, not assumed to produce a real archive from the name alone (`OBJECT` library targets never archive on any generator).
- [ ] A CMake variable/policy-based fix that produces a byte-for-byte-identical failure to before the fix checked against the platform/generator module's own source for an execution-order or policy-branch explanation, before retrying the same class of fix with a different delivery mechanism.
- [ ] A directory-scoped CMake property/command set from a `-C` preload script verified (by minimal local reproduction, if a second attempt at the same class of fix has already failed) to actually propagate into `add_subdirectory()`-included targets, rather than assumed from documentation.
- [ ] Once one instance of an old vendored-code platform-macro assumption (e.g. `TARGET_OS_MAC` meaning "classic Mac OS") is fixed, the whole vendored tree grepped for the same guard condition before calling the fix complete, since the same old library code is often bundled more than once.
- [ ] A checkout step's logged ref/tag read directly before attributing any CI failure to a recent fix being undone, especially for a manually-triggered run against a named tag.
- [ ] A person's report that a build succeeded treated as provisional, not primary evidence, when it's the sole basis for closing an unverified guess.
- [ ] Before reusing an earlier fetch of a project's file as still-current, any newly user-uploaded copy diffed against it to confirm agreement.
- [ ] Any freshly-fetched external file checked for content that could only have come from your own edits earlier in the session (an exact match on custom wording you personally wrote), with a control fetch of an unrelated known-content file run first if anything about the result looks too convenient.
- [ ] Every platform-gated system/vendor-library include grepped for actual use of its namespace/prefix in the plugin's own source before treating it as load-bearing — an unused one found this way flagged as a removal candidate, not just left alone until a build breaks.
- [ ] A second CI run reproducing the identical error signature (same files/lines/columns/count) after a supposed fix treated as proof the fix didn't work, not as ambiguous or inconclusive.
- [ ] Before re-theorizing why a fix didn't work, the exact tag/commit actually built diffed (with line endings normalized) against the patched copy, to rule out "never applied" before concluding "applied but ineffective."
- [ ] A local header-reorder fix checked against the *whole* translation unit's real first-occurrence order for the header in question — every header included earlier in the same file grepped for an existing unconditional include of the same system header — not just the two lines being reordered.
- [ ] An earlier-included SDK/umbrella header checked for its own inline comments about required include order for third-party libraries, before reasoning about generic C/C++ prerequisite order from scratch.
- [ ] When a reordering theory is falsified and the library is confirmed unused, removal offered explicitly as the more verifiable fix over a further reordering guess — especially when no matching toolchain is available in this environment to test the guess first.

## 8. Handoff into documentation

If the same conversation moves on to producing 4D-facing command documentation for the plugin (as opposed to just reviewing/fixing its C++), switch to the separate `4d-plugin-doc-style-guide.md` for the documentation half specifically. The two halves share sources and should stay consistent:

- The doc's parameter tables, optionality claims, and return-shape descriptions should derive from the **same source reading** done during the code review (e.g. "parameter 2 is optional" should be justified by actually seeing the parameter-reading function return a default when the argument is omitted, cross-checked against a real sample `.4dm` file that omits it — not assumed from the manifest syntax alone).
- Any behavior that only exists *after* a fix applied during the review phase must be flagged in the doc as forward-looking — true once the fixed source is built, not necessarily true of whatever binary the reader currently has installed.
- Corner cases inferred by combining evidence (e.g. "this parameter is optional," inferred from both default-value behavior and a sample file that omits it) are stronger and should be called out as inferred-not-explicit if no single source states it outright — same epistemic-hedging principle as §3, applied to documentation claims.
- Whenever a user provides "documentation" or a "spec" for something checkable against a live primary source, and the tools to check it are available, check it before writing derivative material based on it.
- **Command-name cross-references, everywhere in prose, should be links to that command's own heading anchor** — not just in the summary table, but every subsequent inline mention in another command's description, parameter table, or notes. Practical rules:
  - Command headings must have **no backticks in the heading text itself** so the anchor is predictable: lowercase the heading, replace spaces with hyphens, drop punctuation.
  - Link text can still be code-styled even though the heading isn't.
  - Do **not** turn command names inside fenced code blocks into links — links don't render inside code fences, and those are real 4D code samples, not prose references.
  - After adding/changing any such link, grep the finished file for every occurrence of each command's name to confirm nothing prose-facing was missed and nothing inside a code fence was wrongly touched.
